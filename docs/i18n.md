# OpenWard i18n Specification

## Decisions (settled)

| Decision | Choice |
|----------|--------|
| Library | `fluent-templates` (Mozilla Project Fluent) |
| Embedding | Compile-time (`static_loader!`) — all languages baked into the binary |
| Source language | English (keys are English identifiers, every language including French is a translation file) |
| Template access | Translator object (`t`) passed to every template; templates call `t.get("key")` |
| Missing key behavior | Returns the key name itself (never blank); CI check validates all template keys against .ftl files |
| Date/number format | ISO universal: `2026-03-19`, plain digits. Facility-wide, not locale-dependent |
| Locale determination | Per-operator preference, stored in session. Default from profile, overridable at login |
| Legal terminology | Separate layer: compile-time presets + runtime override file on disk |
| Initial languages | English, French, Malagasy |

---

## 1. String inventory

There are approximately **520 translatable strings** in the codebase. They break down into:

### 1a. UI strings (~440)

These are generic interface text that stays the same regardless of country. Examples:

- Navigation: "Dashboard", "Population", "Admission", "Housing", "Count", "Court Calendar", "Logout"
- Form labels: "Surname", "Given names", "Date of birth", "Sex", "Save", "Cancel"
- Table headers: "Name", "Date", "Status", "Action"
- Status/feedback: "Not started", "Submitted", "Balanced", "Unbalanced"
- Error messages: "Invalid date", "Detainee not found", "Internal server error"
- Parametric strings: "held for {$days} days", "Page {$current} / {$total}", "{$count} detainees total"

Where they currently live:
- **19 template files** (~380 strings hardcoded in French HTML)
- **8 handler files** in `web/` (~50 strings constructed in Rust)
- **`filters.rs`** (~10 non-legal strings: sex labels, age groups, date formatting)

### 1b. Legal/domain terms (~80)

These are specific to a country's legal system. A Malagasy prison and a Senegalese prison both use French, but their legal terminology may differ. Examples:

- Detention basis labels: "Police Custody" / "Garde à vue"
- Court purposes: "First Appearance" / "Première comparution"
- Court outcomes: "Acquitted" / "Acquitté"
- Commitment order types: "Remand Order" / "Mandat de dépôt"
- Bail statuses: "Bail Granted" / "Caution accordée"
- Release types: "Sentence Expired" / "Fin de peine"
- Facility statuses: "Present" / "Présent", "Transferred" / "Transféré"
- Flag labels: "No Legal Basis" / "Sans base légale", "Custody Limit Exceeded" / "Dépassement garde à vue"

Where they currently live:
- **`filters.rs`** — all ~80 legal strings are in `*_fr()` match functions

```

├── locales/
│   ├── en/
│   │   ├── ui.ftl              # All UI strings in English (source of truth)
│   │   └── legal.ftl           # Legal terms in generic English
│   ├── fr/
│   │   ├── ui.ftl              # French UI translation
│   │   └── legal.ftl           # French legal terms (generic)
│   └── mg/

│       └── legal.ftl           # Malagasy legal terms
├── legal-presets/
│   ├── fr-MG.toml              # Madagascar-specific legal term overrides
│   ├── fr-SN.toml              # Senegal-specific (example, future)
│   └── README.md               # How to create a new preset
├── src/
│   ├── i18n.rs                 # Translator struct, static_loader!, locale helpers
│   └── ...
└── ...
```

The `locales/` directory is read at compile time by `static_loader!` and embedded in the binary. The `legal-presets/` directory contains TOML files that are also embedded via `include_str!` (compile-time presets), but can be overridden by a file on disk at runtime.

## 4. The Translator struct

File: `crates/openward-server/src/i18n.rs`

```rust
use fluent_templates::static_loader;
use fluent_templates::Loader;
use unic_langid::LanguageIdentifier;
use std::collections::HashMap;
use std::sync::Arc;

static_loader! {
    static LOCALES = {
        locales: "./locales",
        fallback_language: "en",
    };
}

/// Supported languages. Compile-time known.
pub const SUPPORTED_LANGUAGES: &[(&str, &str)] = &[
    ("en", "English"),
    ("fr", "Français"),
    ("mg", "Malagasy"),
];

pub const DEFAULT_LANGUAGE: &str = "en";

/// Legal term overrides loaded at startup.
/// Key: fluent message ID (e.g., "legal-basis-police-custody")
/// Value: the override string
pub type LegalOverrides = Arc<HashMap<String, String>>;

/// The translator object passed to every template.
pub struct T {
    lang: LanguageIdentifier,
    legal_overrides: Option<LegalOverrides>,
}

impl T {
    pub fn new(lang_code: &str, legal_overrides: Option<LegalOverrides>) -> Self {
        let lang: LanguageIdentifier = lang_code
            .parse()
            .unwrap_or_else(|_| DEFAULT_LANGUAGE.parse().unwrap());
        T { lang, legal_overrides }
    }

    /// Look up a UI or legal string.
    /// For legal-* keys, checks runtime overrides first.
    /// Returns the key name itself if not found (never blank).
    pub fn get(&self, key: &str) -> String {
        // Check legal overrides first
        if key.starts_with("legal-") {
            if let Some(overrides) = &self.legal_overrides {
                if let Some(val) = overrides.get(key) {
                    return val.clone();
                }
            }
        }
        // Fall back to compiled .ftl files
        LOCALES.lookup(&self.lang, key)
    }

    /// Look up a string with named arguments.
    /// Example: t.get_with("population-total", {"count": "42"})
    pub fn get_with(&self, key: &str, args: &HashMap<String, String>) -> String {
        let fluent_args: HashMap<String, fluent_templates::fluent_bundle::FluentValue> =
            args.iter()
                .map(|(k, v)| (k.clone(), v.as_str().into()))
                .collect();
        LOCALES.lookup_with_args(&self.lang, key, &fluent_args)
    }

    /// Convenience: look up with a single argument.
    pub fn get_1(&self, key: &str, arg_name: &str, arg_val: &str) -> String {
        let mut args = HashMap::new();
        args.insert(arg_name.to_string(), arg_val.to_string());
        self.get_with(key, &args)
    }

    /// Current language code (for <html lang="...">)
    pub fn lang_code(&self) -> &str {
        self.lang.language.as_str()
    }
}
```

### How `T` is used in templates

Every Askama template struct gets a `t: T` field. Templates call `t.get("key")`:

**Before (hardcoded French):**
```html
<header>Population actuelle</header>
<small>{{ occupancy_percent }}% d'occupation</small>
```

**After:**
```html
<header>{{ t.get("dashboard-current-population") }}</header>
<small>{{ t.get_1("dashboard-occupancy", "percent", occupancy_percent) }}</small>
```

### How `T` is created in handlers

Every handler creates a `T` from the operator's language preference:

**Before:**
```rust
pub async fn dashboard(
    State(state): State<AppState_>,
    headers: HeaderMap,
) -> Result<impl IntoResponse, Redirect> {
    let operator = require_session(&headers)?;
    // ...
    Ok(DashboardTemplate {
        nav: nav_context(&operator, "/"),
        // ...
    })
}
```

**After:**
```rust
pub async fn dashboard(
    State(state): State<AppState_>,
    headers: HeaderMap,
) -> Result<impl IntoResponse, Redirect> {
    let (operator, lang) = require_session_with_lang(&headers)?;
    let t = T::new(&lang, state.legal_overrides.clone());
    // ...
    Ok(DashboardTemplate {
        nav: nav_context(&operator, "/"),
        t,
        // ...
    })
}
```

## 5. Session and language preference

### 5a. Operator data model change

The `Operator` struct in `auth.rs` gains a `language` field:

```rust
pub struct Operator {
    pub id: String,
    pub name: String,
    pub role: String,
    pub language: String,  // "en", "fr", "mg"
}
```

### 5b. Session cookie

Currently the session cookie stores only the operator UUID. It needs to also carry the language. Two options:

**Option A:** Two cookies: `openward_session=<uuid>` and `openward_lang=<lang_code>`. The language cookie can be set/changed independently.

**Option B:** Single cookie with a simple format: `openward_session=<uuid>:<lang_code>`.

Either works. Option A is simpler to update the language without re-authenticating.

### 5c. Login page language

The login page is shown before any session exists. It needs to handle language without knowing the operator. The approach:

1. Login page checks for an `openward_lang` cookie (persists across sessions)
2. If no cookie, check browser `Accept-Language` header
3. If no match, fall back to `DEFAULT_LANGUAGE`
4. Login page includes a language selector (small dropdown or flag icons) that sets the `openward_lang` cookie via a form submission or HTMX swap and reloads the page

The login form itself includes a hidden or visible language field, so when the operator logs in, their language choice is carried forward into the session.

### 5d. Login page template

The login page must be translatable too. Since it uses its own `<html>` tag (not `base.html`), it gets its own `t: T` constructed from the pre-session language detection:

```html
<html lang="{{ t.lang_code() }}" data-theme="light">
<!-- ... -->
<label for="language">
    {{ t.get("login-language") }}
    <select name="language" id="language">
        {% for (code, name) in languages %}
        <option value="{{ code }}" {% if code == t.lang_code() %}selected{% endif %}>
            {{ name }}
        </option>
        {% endfor %}
    </select>
</label>

<label for="operator_id">
    {{ t.get("login-operator") }}
    <select name="operator_id" id="operator_id" required>
        <option value="" disabled selected>{{ t.get("login-select-operator") }}</option>

        {% endfor %}
    </select>

```

## 6. Legal term override system

### 6a. Compile-time presets

Stored in `crates/openward-server/legal-presets/` as TOML files. Embedded into the binary via `include_str!` in `i18n.rs`.

Example: `legal-presets/fr-MG.toml`

```toml
# Madagascar-specific French legal terminology
# These override the generic French translations in locales/fr/legal.ftl

[overrides]
legal-basis-police-custody = "Garde à vue"
legal-basis-remand = "Mandat de dépôt"
# Only include terms that differ from generic French.
# Omitted keys fall through to locales/fr/legal.ftl.
```

The presets are loaded at startup and stored in memory:

```rust
pub fn load_preset(name: &str) -> HashMap<String, String> {
    let toml_str = match name {
        "fr-MG" => include_str!("../legal-presets/fr-MG.toml"),
        "fr-SN" => include_str!("../legal-presets/fr-SN.toml"),
        // ...
        _ => return HashMap::new(),
    };
    parse_legal_overrides(toml_str)
}
```

### 6b. Runtime override file

A facility can place a file at a configurable path (e.g., `OPENWARD_LEGAL_TERMS=/etc/openward/legal-terms.toml`). Same format as presets. If present, it takes highest priority.

Lookup order:
1. Runtime override file (if it exists and has the key)
2. Compile-time preset (if a preset is selected and has the key)
3. Compiled `.ftl` file for the operator's language

### 6c. Facility setup

A new env var or config option: `OPENWARD_LEGAL_PRESET=fr-MG`. At startup, the server loads the preset and merges it with any runtime override file. The result is stored as `LegalOverrides` in `AppState`.

### 6d. Legal overrides are language-independent

An important subtlety: the override file contains final display strings, not translation keys. If a Madagascar facility uses the `fr-MG` preset, and an English-speaking operator logs in, the legal terms should still appear in English (from `locales/en/legal.ftl`), not in the French override.

This means the override system needs to be keyed by **(key, language)**, not just key.

Revised TOML format:

```toml
# legal-presets/fr-MG.toml
# Madagascar-specific legal terms

[fr]
legal-basis-police-custody = "Garde à vue"
legal-basis-remand = "Mandat de dépôt"

[mg]
legal-basis-police-custody = "Fisamborana ara-polisy"
legal-basis-remand = "Baiko fitanana"
```

And the `T` struct's override lookup becomes:

```rust
pub fn get(&self, key: &str) -> String {
    if key.starts_with("legal-") {
        if let Some(overrides) = &self.legal_overrides {
            // Check for language-specific override: "fr:legal-basis-remand"
            let lang_key = format!("{}:{}", self.lang.language, key);
            if let Some(val) = overrides.get(&lang_key) {
                return val.clone();
            }
        }
    }
    LOCALES.lookup(&self.lang, key)
}
```

## 7. Template migration plan

### 7a. What changes per template

Every template file needs:

1. All hardcoded French strings replaced with `{{ t.get("key") }}` calls
2. Parametric strings use `{{ t.get_1("key", "arg", value) }}` or `{{ t.get_with("key", args) }}`

The corresponding template structs in `templates.rs` gain a `t: T` field.

### 7b. What changes per handler

Every handler in `web/` needs:

1. Extract the operator's language from the session
2. Construct a `T` instance
3. Pass it to the template struct
4. Remove all inline French string construction — replace with `t.get()` calls for any strings the handler builds (dashboard alerts, count status, etc.)

### 7c. What happens to `filters.rs`

The entire `filters.rs` file is **deleted**. Every function in it (`basis_label_fr`, `flag_label_fr`, `sex_label_fr`, etc.) is replaced by `t.get("legal-*")` calls in the handlers or templates that used them.

### 7d. What happens to `templates.rs` display structs

Display structs like `DetaineeSummaryDisplay`, `BasisSegment`, `AlertDisplay`, etc. currently contain pre-resolved French strings (e.g., `label: String`). After migration, those `label` fields contain Fluent **keys**, not display strings. The template resolves them:

**Before (BasisSegment):**
```rust
BasisSegment {
    label: "Garde a vue".to_string(),
    count: overview.basis_breakdown.police_custody,
    css_class: "basis-police".to_string(),
}
```

```html
<span>{{ segment.label }}: {{ segment.count }}</span>
```

**After:**
```rust
BasisSegment {
    label_key: "legal-basis-police-custody".to_string(),
    count: overview.basis_breakdown.police_custody,
    css_class: "basis-police".to_string(),
}
```

```html
<span>{{ t.get(segment.label_key) }}: {{ segment.count }}</span>
```

Alternatively, keep resolving in the handler if you prefer:
```rust
BasisSegment {
    label: t.get("legal-basis-police-custody"),
    count: overview.basis_breakdown.police_custody,
    css_class: "basis-police".to_string(),
}
```

The first approach (keys in struct, resolve in template) is more consistent and means the handler doesn't need `t` at all for these structs. The second approach (resolve in handler) keeps templates simpler.

Either works. The spec does not mandate one over the other — pick whichever feels cleaner during implementation and use it consistently.

## 8. Date formatting

All dates use ISO 8601 format: `2026-03-19`. This replaces the current `%d/%m/%Y` format used in `filters.rs` and handlers.

The `format_date` function in `filters.rs` is replaced with:

```rust
pub fn format_date(date: &chrono::NaiveDate) -> String {
    date.format("%Y-%m-%d").to_string()
}
```

Or inline in templates: `{{ date.format("%Y-%m-%d") }}`

Datetime stamps (e.g., dashboard "as of") use: `2026-03-19 14:30` (no seconds, no timezone display — the Pi's clock is the single source of truth).

## 9. CI key validation

A build-time or CI-time check that ensures:

1. Every `t.get("...")` and `t.get_1("...")` call in every `.html` template file references a key that exists in `locales/en/ui.ftl` or `locales/en/legal.ftl`
2. Every key in `locales/en/ui.ftl` and `locales/en/legal.ftl` is used in at least one template or handler (no dead keys)
3. Every key in `locales/en/` has a corresponding entry in `locales/fr/` and `locales/mg/` (no missing translations)

Implementation: a Rust integration test or `build.rs` step that:
- Parses all `.html` files with a regex for `t\.get\("([^"]+)"\)` and `t\.get_1\("([^"]+)"` patterns
- Parses all `.rs` handler files for the same patterns
- Parses all `.ftl` files to extract defined keys
- Reports any mismatches

This runs in CI and fails the build if any language is incomplete or any template references a nonexistent key.

## 10. Adding a new language

### For a language already in the binary (e.g., Malagasy)

No action needed. An operator selects "Malagasy" at login or in their profile.

### For a new language not yet in the binary

1. Create `locales/<code>/ui.ftl` and `locales/<code>/legal.ftl` by copying the English files and translating
2. Add the language to `SUPPORTED_LANGUAGES` in `i18n.rs`
3. Optionally add legal presets in `legal-presets/`
4. Rebuild and deploy

The `.ftl` file format is designed for translators — it is readable without programming knowledge. A contributor workflow:

1. Copy `locales/en/ui.ftl` to `locales/sw/ui.ftl` (Swahili example)
2. Translate each line: `nav-dashboard = Dashibodi`
3. Submit as a pull request or email the file
4. Maintainer adds it, rebuilds, releases

### For facility-specific legal terms

1. Create or edit the legal override file on the Pi (e.g., `/etc/openward/legal-terms.toml`)
2. Restart the server
3. No rebuild needed

## 12. Open questions

These are not blockers but should be decided during implementation:

1. **Should the operator's language preference persist in the database** (once real auth exists), or is the cookie sufficient for now?

2. **Should HTMX fragment responses inherit the language** from the parent page's session, or should each HTMX request independently resolve the language? (The session cookie is sent with HTMX requests by default, so this should work automatically — but it needs to be verified.)

3. **For the Malagasy translation**: who does it? Is there a specific person, or should the .ftl files be prepared with English placeholders and left for future translation?

4. **Should the legal preset name be visible to operators** (e.g., "Madagascar legal terms" in a settings page), or is it a pure admin/deployment concern?
